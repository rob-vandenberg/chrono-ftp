## Open questions

1. Is `rsync` over SSH fast enough against FTP? Waits for the test on a real FTP server.
2. [Not tested] An FTP connection may need a second login to browse during a transfer.
3. Right after a folder is made, `setRootPath` once gave an invalid index in a probe. The tree of the left side still uses that call.
4. Known limits: over FTP a link can't be resolved, so a stop while writing through one leaves a half file; the folder tree of the left side can't show a folder whose name is not valid UTF-8, though the list can; a server file can't be dragged to a file manager; a name that is not valid UTF-8 can't be opened in another program or sent to the Trash.
5. Known limits of selection and keys (0.0.40):
   1. The desktop may take some keys before Chrono FTP sees them: often Alt+F7 (moving a window) and Ctrl+F1 to Ctrl+F4 (virtual desktops). The file manager key set finds files with Ctrl+F; the sort keys stay on their own keys.
   2. The column header menu is kept per tab only where "Each tab keeps its own sort order and columns" is on; otherwise one layout for all tabs, as the columns were before.
   3. A right-button drag and its menu were tested through the drop itself; a real drag with the right button on the desktop is still to be tried by hand.
   4. Sorting by extension (Ctrl+F4) is not kept after a restart: the name order comes back.
6. Known limits of the transfers (0.0.13):
   1. On FTP, a file that appears between the last check and the rename can be replaced.
   2. An FTP server that lists a link as a plain file can't be told apart: an upload replaces such a link with a file.
   3. An FTP server that gives neither a type of its own nor a full mode shows a pipe as a plain file, and a download of it waits until it is stopped.
   4. On FTP, and on SFTP servers without `fsync@openssh.com`, a move checks the arrived copy by its size and date only; the hover text says so.
   5. An append broken off by a lost connection is left as it is, unless nothing else can be in the file.
   6. On FTP without MLST, the listing kept during a job doesn't see what others add meanwhile; the check before each rename does.
   7. Whether an SFTP server can put a file on its disk is read from a private attribute of asyncssh; if that changes, the program says it checked size and date only.
   8. The notes of append owners use a lock file; on Windows the notes of other processes count as ended.
   9. On the rsync way, a file agreed to be replaced is looked at again right before rsync starts; a change during rsync's own run is not seen.
   10. With "Ask before replacing" off, rsync skips a file whose size and date match, although its content may differ.
   11. Names of our own are kept within 255 bytes; a file system with a lower limit can still refuse them.
   12. On FTP, a picked file that the server refuses to tell about can't be told from one that is gone: both answer 550, and the job says it is no longer on the server.
   13. "The same place" of two queue items on a server means the same login: an FTP and an SFTP tab, or two users, on one machine count as different sides.
   14. With a status bar speed limit set, every start or end of another item restarts running rsync items, as their share changes; only time is lost. A whole-folder rsync run without a look-over and without kept dates can send earlier files again after a limit change or a resume.
   15. Over a real SSH server, the server's rsync may put its unfinished copy away a moment after Chrono FTP removed that folder (resume Never); Delete tries again, and tidying takes the rest an hour later.
   16. A file split in parts asks for its further logins only when it starts; places that free up later are not used for it.
7. The live test on the SFTP test account without a shell has not run for 0.0.12 and 0.0.13.
8. Known limits of the looks (0.0.39):
   1. Masks are simple name patterns (`*`, `?`, `[...]`, a / for folders); sizes, dates and paths in a mask come with block FD.

10. Known limits of Properties and server actions (0.0.37):
   1. The SFTP extension copy-file is not used, as asyncssh does not tell whether a server offers it; copy-data is. Without a shell only files are copied on the server.
   2. Owner and group change only with a shell; without one they are shown and greyed. Over the protocol a file whose rights the server did not tell is left as it was when a box says "leave as it is".
   3. Change Password reads passwd's questions in English (`LC_ALL=C`); a passwd that asks in another way than "current/old" and "new/retype" ends calmly without a change. It was tried only against the fake server's stand-in for passwd (OR-26), never on a real account; so was Install My Public Key.
   4. A password shorter than a word inside the server's answer is taken out only where it stands as a word of its own.
   5. Size in Properties counts the files only, not what is in the folders (folder sizes come with block FE).
   6. The live tests of block FM ran on this computer's SSH server only (`tests/test_live_serveractions.py`).
11. Known limits of block FP (0.0.38):
   1. Over SFTP the free space comes from statvfs@openssh.com or `df`; the space-available request can't be sent through asyncssh, so a server that offers only that one shows "unknown" without a shell.
   2. The key exchange is noted through a part of asyncssh that is not public; another version of asyncssh shows it as "unknown" and nothing else changes.
   3. A value that only looks like a password is not known to be one: the log replaces the passwords Chrono FTP itself uses, FTP's PASS line, private key blocks and values named password, passphrase or secret; a password typed into a server's own program is never seen by Chrono FTP.
   4. The update check reads at most ten pages of tags (1,000 versions).
   5. A Server Information request whose tab closes meanwhile leaves its window saying "Asking the server…".
12. Known limits of masks (0.0.41):
   1. A server's text files get one LF per line; a server that keeps text with CRLF (Windows) is not recognised and gets LF too.
   2. A text file to upload is first converted into a copy in `~/.local/state/chrono-ftp/converted/`, so a very large text file needs that much room on this computer for a moment.
   3. The order of the presets, which decides the one that fits first, is the order they were made in; it can't be changed yet.
   4. Num+ and Num− need a keyboard with a number pad; Select by Mask… and Unselect by Mask… in the Select submenu work without.
13. Known limits of hashes and sizes (0.0.42):
   1. A stop ends the work at once on this side, and a count or shell checksum on the server with its whole process group where its shell can tell that group (by `ps` or `/proc`), else by the SSH signal alone; a check-file or HASH the server has started may run on there until the server notices its channel or login closed, which the stop does at once.
   2. Folder sizes on the server through one command need GNU find (`-printf`) and awk; elsewhere the listings are walked, which over FTP lets a request of the person wait for one listing at most.
   3. Over SFTP the extension names of the server's hello are read through a part of asyncssh that is not public; another version of asyncssh shows check-file as not offered, and nothing else changes.
   4. Shift+Space was tested through the list itself; a real Shift+Space on the desktop is still to be tried by hand.
14. Known limits of synchronize (0.0.43):
    1. Apply for two folders on this computer runs on a thread of its own and says in the status bar how far it is, not through the queue: a queue item needs a connection, and two local folders have none.
    2. The date precision is read from the dates the scan saw on the other side: where every date it saw is a whole minute, dates are compared by the minute, so a difference of less than a minute is then no difference.
    3. A move is found only where exactly one file on each side has that size; two one-sided files of the same size go the plain way (a copy and a delete).
    4. "Look Inside the Files" (block FE's step) still works on the rows of the same size, next to the "They hold exactly the same thing" choice of block FF; the two do the same work in two places.

    7. Mark Differences, Reverse and the checklist's sorting were tested through the window's own widgets; they have not been tried by hand on the desktop.
    8. A move row can't be reversed: Reverse is greyed with its reason, since the file is on one side only.
    9. The files inside a folder that is to be deleted are named in the question only where the background count of FF-06 already knew them; otherwise the question says plainly that it does not know.
    10. After a run of two folders on this computer the list is the one from before that run; Start is greyed and says to press Compare Again for a fresh look.
    11. Abort for two folders on this computer ends after the step it is busy with; a single very large file being copied is still finished first, and the button's hover text says so.

    13. A window test waits for a tab to have settled (`settled_tab`), never for `alive` alone: `alive` is set in the same step that asks for the first listing, so a test that goes on at `alive` ends with that request still in flight.
15. Known limits of tabs and workspaces (0.0.45):
    1. The remembered order of the tabs is kept by connection name: a connection that was never dragged opens its tab at the end, and a connection renamed in the connections window loses its remembered place.
    2. Two tabs of one connection (Duplicate Tab) both write back the last folders when they close, where that connection remembers its folders; the one that closes last wins.
    3. A tab name is kept with the connection, so both tabs of a duplicated connection carry the same name; a name of its own per tab is not kept.
    4. Opening a workspace whose connection already has a tab leaves that tab's folders as they are; it never moves an open tab to the folders the workspace saved.
    5. A folder pasted onto a folder of the same name is merged into it after the question: files of the same name are replaced, the others stay. A folder is never replaced as a whole, so nothing in it is lost (G-2).
    6. Pasting within one server never overwrites: the server's copy refuses a name that is taken and says which, as Copy To does. Between two servers the upload asks the overwrite question as any transfer does.
    7. A copy on its way between two servers keeps its fetched file in a temporary folder of this computer (`chrono-ftp-copy-…`); closing Chrono FTP removes it, but a crash in between leaves it to the system's own clean-up of temporary files. The Clean Up window does not list it.
    8. Dragging a tab, dropping files on a tab, the middle mouse button and the tab keys were tested through the window's own events; a real drag and a real middle click on the desktop are still to be tried by hand.
    9. The copy the server makes within one server was tested as the route only (which way a paste takes): the command itself is the one Copy To runs, which the fake server can't be used for, as its shell acts on this computer's own paths.
    10. A paste within one server and a paste into a folder here both run in their own window with Start and Abort; a paste that goes to another server runs in the queue, which opens by itself and can be stopped there. Within one server a copy that replaces something needs a shell: without one that item says so and is left.
    13. A copy that replaces something needs room for both for a moment: the new copy stands next to the old one until it is whole.
    14. A workspace opens again exactly the tabs it saved, two tabs on one connection included; a tab that is already open covers one of them.
    15. Chrono FTP killed in the middle of a copy that replaces something (between moving what was there aside and putting the copy in its place) leaves that file or folder under its name with ".chrono-ftp-old" at the end, and the real name missing for that moment. Nothing is lost, and the next paste of that name refuses and says where it is and to rename it back, so no recovery runs by itself.
    11. The questions before something is written over are all asked before the copying starts, file by file as a transfer asks; something that appears in that moment is left as it is and named at the end as one that could not be done.
