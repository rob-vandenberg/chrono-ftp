# STATUS.md

## Now

Version 0.0.50: the Settings window keeps what it does not show. Pressing OK used to throw away every setting that window has no field for, because it built fresh settings out of its own fields alone. Six things a person had chosen elsewhere went back to their standard the moment they pressed OK anywhere in Settings: the checksum algorithm last used in Properties, every choice of the Synchronize window, what the last scan of each folder pair counted, the order the tabs were dragged into, the folders of the connection list that stand open, and the connection New starts from. The window now keeps the settings it was given and changes only the values it shows, so nothing it does not show can be lost, and no setting added later can be lost either. Because one setting can change while the window stands open — the connection that was last live — the main window hands `chosen()` the settings of this moment, which also took the place of the one patch that used to put that single value back by hand (`src/chrono_ftp/ui/settingsdialog.py`, `src/chrono_ftp/ui/windowlayout.py`). Three tests guard it, each proved to fail on 0.0.49.

Version 0.0.49 before it: the look. Chrono FTP is no longer dark and nothing else. The General page of Settings has a **Look** choice: The same as my desktop, Dark, or Light. A fresh installation follows the desktop, and so does one that is updated, because a settings file written before this version holds no look, and a desktop that tells the program nothing counts as dark, which is the look Chrono FTP always had. Following the desktop means while the program runs: turning the desktop light turns Chrono FTP light at once, and a person who chose Dark or Light keeps that whatever the desktop does. A change never waits for a restart: the palette, the menus and the icons are drawn again at once, the tab bar paints its greys from the look of the moment, and the right side, the lock in the status bar and the connection list, which each keep a picture or a palette of their own, are told again. Both looks live in `src/chrono_ftp/core/colours.py` and nowhere else, as two complete sets of the same names; reading the desktop brings in one word, light or dark, never a colour (OR-9). An icon now draws itself in the colour of the text of the moment, through an icon engine, so no icon can be left behind in the old look and nothing has to be put back on the toolbars; what has been drawn is kept per look, so a toolbar draws from memory. The colours a person chose stay exactly as they chose them on both looks, a connection's colour and the colours of a file rule alike, with black or white text by the brightness of the background; only the colours offered first for a new file rule follow the look (D-105, D-007). Not yet tried by hand on the desktop, and the light look has not been seen by a human: the screenshots in `scratchpad/` are what the program draws.

Version 0.0.48 before it: the installers. The folder `packaging/` turns Chrono FTP into one `.deb` (98 MB) and one `.rpm` (100 MB), each carrying its own Python 3.14, Qt and the program in `/opt/chrono-ftp`, so the person installs one file and nothing else. Nuitka compiles the program inside an Ubuntu 22.04 container, because a program built on an older system also runs on newer ones and not the other way round; nFPM packs that folder. Everything the build needs from outside is fetched once into a builder image and a wheel cache, so a build downloads nothing. The packages name `rsync` and the SSH client as dependencies (`openssh-client` on Debian and Ubuntu, `openssh-clients` on Fedora and openSUSE, both proved in a bare container) and let the person's own package manager install what is missing; no script inside a package ever runs a package manager itself. The terminal program and `xdg-open` stay out of the dependencies and are detected at run time as before. The program folder carries the wheel's own package information, because without it the About window has no version, no repository address and no licence text; the build checks all three and refuses to make a package without them. App information (AppStream) names its package, or software centres do not list Chrono FTP as installed and it cannot be removed there. Both packages were installed and started in a bare Ubuntu 22.04 and a bare Fedora 43 as a normal user. Nothing is on the GitHub release page: that waits for `./build-release.sh --upload`, which only the owner gives, for a version the owner installed and tried (D-104, OR-29, OR-30, `packaging/PACKAGING.md`).

16. Known limits of the connection list (0.0.47):
    1. A folder of the list exists only as long as a connection stands in it: the last connection that leaves takes the folder with it, and an empty folder can't be made or kept.
    2. A folder itself can't be dragged, renamed or deleted as a whole; a connection is moved one at a time, by dragging it or by typing its name.
    3. Dragging in the list was tested through the window's own drop events; a real drag with the mouse on the desktop is still to be tried by hand.
    4. Typing in the list finds a connection, never a folder, and matches the connection's own name, not the folder before it.
    5. The remembered place of a tab, the bookmarks and the location profiles are kept by connection name, so a connection moved into a folder keeps its bookmarks and profiles (the window moves them with the name) but loses the place its tab was dragged to.
    6. The import reads `~/.ssh/config` itself only: a file it names with Include is not read, and every server of such a file is then offered unticked with that reason. Of the settings it does read, only the name, the server, the port, the user and the key file come over; everything else of a Host section is left, and the keywords that would change the login refuse the server whole.
    7. A Host pattern is matched as a file mask, which does a little more than OpenSSH's own patterns; the characters where they differ do not appear in server names.
    8. The host keys of `~/.ssh/known_hosts` are read by asyncssh, hashed entries included; a key in it that no longer matches the server gives the same refusal as one of Chrono FTP's own ("the host key has changed").
    9. A tab opened from a pasted address is in no list: its user name is never written back, its password is never stored, and the connections window can't start on it. Its bookmarks, typed paths and the order of its tab are kept under the name the tab got, as any tab's are.
    10. The note is plain text and is kept whole in the connection list file; the file holds nothing secret, so a note should hold no password (the window says so nowhere yet).
    11. The address of a connection takes its remote starting folder only where that is a path from the root; a relative one (`public_html`, `~/x`) is left out, so the address means the home folder of the login.
    12. A password typed in an address is used for that one login; a second paste of the same address opens a second tab with its own login, and neither of them is in any list.
    13. The import works out ~, $HOME, ${HOME}, %d, %u and %h in a setting; any other token of OpenSSH's own refuses that server with its reason, as a port that is no port does.
    14. A password in a pasted address that holds a slash is written %2F, and an @ in a folder beside a port is written %40: where what stands before the first slash can be read as a server with a port or as a user name with a password, Chrono FTP reads neither and says so, so sftp://h:22/a@b must be written sftp://h:22/a%40b. An @ in a folder without a port is a folder.
    15. A server name in another language is kept in the form the network uses (xn--…), which is what the address and the connection then show; the name as the person typed it is not kept.
    16. The import reads the SSH settings of one server as a whole: where one setting of it can't be read, that server comes over not at all, never in part.
    17. A move is refused while any of the four settings files can't be written; it is not tried file by file, so a move either carries everything that follows the name or changes nothing.
    18. A tab opened from an address logs under a name of its own ("127.0.0.1 (from an address)"), so it never writes into the log of a connection that carries the name it was given; two such tabs of one address do share their log, as two tabs of one connection do.
    19. A setting of ~/.ssh/config that holds more than one word without quotes refuses its server: OpenSSH takes only the first word for some keywords, and which one is meant can't be told.
